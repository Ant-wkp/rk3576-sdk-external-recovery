# 原生 updateEngine 启动检查：问题记录

本文件为本轮新增记录，不替换旧独立 OTA 或 U-Boot DM 验收报告。

## 1. 停狗错误不能只等待 WDT

复位 assert 已成功、deassert 失败时，硬件可能已停，但用户态接口返回失败。
此时只停止喂狗可能永远不复位。实现保留已确认槽，记录关闭失败并请求正常
重启，等待最多 15 秒；硬件仍运行时由 WDT 继续兜底。隔离测试已覆盖，
Linux 实板已证明能停止：两槽检查成功后均为 `inactive`；一次持续运行到
uptime 295.49 秒，超过两个 89.479 秒周期，没有用户态 feeder，也未复位。

## 2. U-Boot 二进制同时包含短版本和完整版本

首轮发布生成器匹配到 `U-Boot 2017.09` 和带日期的完整 banner，拒绝生成
发布文件。修正为仅提取带日期的完整 banner，并去重、拒绝不同完整版本。
实际构建及包含两种字符串的夹具均通过。

## 3. SDK 日志管道吞掉 overlay 错误

首轮 `sdk-v1.log` 返回 0，但记录了发布生成失败，最终镜像缺少发布文件。
该轮镜像不接受、不部署。未修改通用 SDK 脚本；本板型 defconfig 追加
`check-boot-install.sh`，在通用 post-build 之后校验程序、启动入口、发布
信息及旧 feeder 残留。门禁正反例与第二轮完整 SDK 构建通过。

## 4. 宿主机 fortify 重定向绕过测试 realpath 替身

宿主机编译将 realpath 调用重定向为 `__realpath_chk`，导致测试未进入替身。
仅测试编译关闭该重定向，生产编译加固设置不改。真实设备及重启调用仍在
测试链接层全部隔离，不向生产程序增加模拟参数。

## 5. 实板串口被 Tabby 占用

早期 `/dev/ttyUSB1` 由 Tabby PID 1089850 持有，当时停止板端操作；没有
强制终止用户进程或打开第二个接收器。用户断开连接、随后确认开发板断电后，
重新核对继电器 off，先启动唯一接收器再上电，完成了本轮全部板端验收。

## 6. 目录与编译器路径

`device/rockchip/rk3576` 实际链接到 `.chips/rk3576`，发布脚本从物理目录
定位 SDK。首次独立 V2 DTB 检查的工具链目录名写错，已按实际目录修正，
重新编译成功；该失败不作为任何编译通过证据。

## 7. 根分区只读不能等同于槽位未知

第一版把根的 rw 健康状态混入实际槽位识别，根只读时会无法执行立即回退。
现已分离：健康检查要求 rw ext4，但失败处理仍可根据实际根设备号和同盘
misc 识别当前槽。只读根立即回退；未知根或异盘 misc 不修改元数据。
真实源码隔离测试及 ARM64 编译通过。

## 8. 完整 SDK 构建可能沿用旧 Recovery 缓存

V2 首轮生成的 updateEngine 摘要仍为旧值 `86387cff...`，与新源代码不符。
实际 build/recovery-develop/boot_check.c 也与当前源码不同，证明仅切换板型
不会刷新本地包。使用 `./build.sh bmake:recovery-rebuild` 单包重建，未清空 SDK。
增加板型安装门禁：检查源码副本一致、二进制不早于输入文件；单纯同步源码
但没有重新编译也拒绝。此后两套当前镜像的程序摘要为 `788dd953...`。
旧 v1/、v2-final/ 保留历史证据，但明确禁止用于本轮部署。

## 9. FIT 的空签名模板不是实际签名

SDK ITS 在未签名镜像中也保留 signature 节点及 algo/key-name-hint。
不能仅凭节点名称认定固件已签名或上锁。检查器拒绝实际 value 属性，允许
无 value 的模板。已用实际两套 FIT 及正反例验证；未进行任何签名或 OTP 操作。

## 10. 不能把“请求 60 秒”当成实际看门狗周期

共享 SPL 报告 24 MHz、TOP15、89479 ms；Linux 接口取整报告 89 秒。
检查进程 SIGSTOP、正常重启 exec 失败、元数据 CRC 读取错误三次实测分别
约 89.55、89.60、89.50 秒复位。均没有人工重启或断电，BL31 记录
`reset status: 0x1050`，而正常软件重启为 `0x1`。

## 11. 下一次启动后的 metadata 不是回退瞬间的快照

SPL 会更新 `last_boot`。仅比较回退前与下一次 Linux 启动后的扇区，可能
误以为用户态回退修改了旧槽或 `last_boot`。本轮测试库只读保存实际接管
与 reboot 调用前的两个 512 字节快照，证实只有失败槽字段及 CRC 改动，
旧槽四字节、`last_boot`、保留区与 480 字节尾部都保持。

## 12. 故障注入不能遗留到正式启动路径

测试只对一个原生检查进程使用 LD_PRELOAD，不改全局 preload 或生产代码。
一次性 init 在调用检查前原子恢复正式脚本并同步，真实 WDT 复位后自动回到
正常检查。最终两槽脚本摘要均为 `530fd9bd...`，程序摘要均为 `788dd953...`，
没有 pending。测试资产移存 userdata 的非启动归档目录，可恢复，不删除历史。

## 13. 原生升级器的继承限制不在本轮验收范围

本轮没有改原生刷写/差分/下载算法，也没有引入旧独立工程事务与发布缓存。
原 `--reboot` 仍继承 SysRq 立即重启实现，实板升级验收不使用该参数，升级
成功后另行正常 `reboot`；新增启动检查失败分支使用正常 `/sbin/reboot`。
旧代码 `sprintf` 等告警仍在，不能因本轮成功就宣称恶意包安全、差分事务、
断电原子性或签名认证已解决。CRC、fsync 和读回不是断电原子写保证。

## 14. 原生日志中的源名称和写入意图不能当作实际目标

官方包只有 `*_a` 源镜像，A→B 时日志仍可显示 `now write uboot_a to
/dev/block/by-name/uboot_b`：源名称回退不改变已选定的 B 目标路径。最终
证据审计按目标路径核对，不误要求日志一定变成 `uboot_b` 源名称。
原 `RK_ota_start()` 还会先打印 parameter 的 `now write`，随后立即进入
普通 OTA 跳过分支并打印 `ingore misc.`，并未调用 `flash_parameter()`。
因此不能只搜索 `now write parameter` 就认定改了 GPT。真实源码隔离测试、
跳过日志及共享前8MiB摘要保持共同支撑本轮不写GPT的结论；没有为美化日志改算法。
